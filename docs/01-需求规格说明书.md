# 校园实验室智能预约与安全管理平台需求规格说明书

## 1. 文档说明

### 1.1 编写目的

本文档用于明确校园实验室智能预约与安全管理平台的建设范围、用户角色、业务规则、功能需求、非功能需求和验收标准，为数据库设计、接口开发、页面实现、测试和毕业论文撰写提供统一依据。

### 1.2 项目范围

系统采用前后端分离方式开发：后端基于 Spring Boot 3 和若依框架，前端基于 Vue 3、Vite 和 Element Plus，数据库使用 MySQL，缓存使用 Redis。若依负责登录认证、JWT、用户、角色、菜单权限、日志等通用能力；本项目自行开发实验室、设备、预约、安全考试、审核和信用分业务。

本项目分为两个阶段：

第一阶段完成不依赖大模型的传统业务闭环；第二阶段接入 Spring AI，实现安全知识问答、业务查询和受控智能预约。第一阶段必须能够独立运行和演示。

### 1.3 术语定义

| 术语 | 定义 |
| --- | --- |
| 实验室 | 可供学生进行实验的场地资源，具有容量、开放时间和安全等级。 |
| 设备 | 安装或存放在实验室中的仪器设备，可被预约使用。 |
| 预约 | 学生针对特定实验室和时间段提交的使用申请。 |
| 审核 | 指导教师对需要审核的预约申请进行通过或驳回。 |
| 安全考试 | 学生在预约高风险实验前必须完成的实验室安全考核。 |
| 信用分 | 用于反映学生预约和实验行为情况的分值。 |
| Agent | 能理解自然语言并在权限约束下调用后端业务工具的大语言模型应用。 |

## 2. 用户角色与权限

### 2.1 学生

学生可以登录系统，查看实验室和设备信息，查询指定日期与时间段的空闲资源，参加安全考试，提交和取消自己的预约，查看审核结果、信用分和违规说明，并使用智能助手查询信息或生成预约草稿。

### 2.2 指导教师

指导教师可以查看待审核预约，查看申请人的安全考试状态、信用分、实验内容和设备需求，对预约进行通过或驳回并填写原因；可以查看本人负责的实验安排，但不能修改系统基础资源。

### 2.3 实验室管理员

管理员可以维护实验室、设备、开放时间、安全等级和设备状态，维护安全考试题库，查看预约和审核记录，处理信用分流水和违规记录，并查看资源使用统计。

### 2.4 系统管理员

系统管理员使用若依已有的用户、角色、菜单和接口权限管理功能，负责账号、角色、菜单和系统参数维护。第一期可以由实验室管理员兼任系统管理员。

## 3. 业务流程

### 3.1 普通预约流程

```text
学生登录
  -> 查看实验室和设备
  -> 选择实验室、日期、时间和人数
  -> 填写实验名称及设备需求
  -> 后端检查开放时间、容量、时间冲突、考试状态和信用分
  -> 生成待审核或直接通过的预约
  -> 教师审核（如规则要求）
  -> 学生查看结果
  -> 按规定签到、完成实验或取消预约
```

### 3.2 预约状态

| 状态 | 含义 | 可执行操作 |
| --- | --- | --- |
| `PENDING` | 已提交，等待教师审核或系统处理 | 教师审核、学生按规则取消 |
| `APPROVED` | 审核通过或无需审核 | 签到、完成、取消 |
| `REJECTED` | 教师驳回 | 查看原因，不可签到 |
| `CANCELED` | 学生或管理员取消 | 只能查看历史记录 |
| `COMPLETED` | 实验已结束 | 查看记录 |

### 3.3 取消规则

学生只能取消本人预约；已完成或已取消的预约不能重复取消；距离开始时间少于系统规定时间的预约是否允许取消由管理员配置；无故取消或多次爽约可触发信用分扣减。

## 4. 功能需求

### 4.1 登录与权限

系统应复用若依登录和 JWT 认证机制。登录成功后前端保存令牌，后续请求在 `Authorization` 请求头中携带令牌。后端根据角色和菜单权限控制接口访问；任何业务接口均不得仅依赖前端隐藏按钮实现权限控制。

### 4.2 实验室管理

管理员可以新增、编辑、查看、停用和恢复实验室。实验室字段包括编号、名称、类型、位置、容量、安全等级、开放时间、状态和说明。停用实验室不能创建新的预约，但历史预约仍可查询。

### 4.3 设备管理

管理员可以维护设备编号、名称、类型、所属实验室、数量、可用状态和是否需要培训。设备必须属于一个实验室；维护或停用状态的设备不能被新预约选择。

### 4.4 预约管理

学生提交预约时必须填写实验名称、实验室、开始时间、结束时间、参与人数、设备需求和实验说明。后端必须进行参数校验和业务校验，校验失败时返回明确原因。

时间冲突判定规则为：对同一实验室，若已有有效预约满足 `已有开始时间 < 新结束时间` 且 `已有结束时间 > 新开始时间`，则存在冲突。有效预约至少包括 `PENDING` 和 `APPROVED`。

### 4.5 教师审核

高风险实验、需要教师指导的实验或管理员配置为必须审核的实验必须进入审核流程。教师审核时可以查看实验名称、时间、实验室、设备、人数、安全考试和信用分。审核通过后预约变为 `APPROVED`；驳回必须填写原因。

### 4.6 安全考试

学生可以参加安全考试并查看成绩。系统保存考试时间、成绩、是否通过和有效期。预约高风险实验时，后端必须检查学生是否存在有效且通过的考试记录；没有通过记录时拒绝预约并提示考试入口。

### 4.7 信用分

每个学生拥有当前信用分和信用分流水。正常完成实验不扣分，违规、爽约或未经许可取消可按规则扣分。信用分不足时，系统可以禁止提交预约或要求教师审核。所有分值变化必须保存原因和关联业务记录。

### 4.8 智能助手（二期）

智能助手支持安全知识问答、实验室查询、设备查询、安全考试状态查询、信用分查询、预约记录查询和预约草稿生成。大模型不能直接访问数据库；写操作必须通过白名单 Java 工具、当前登录用户身份、后端业务规则和用户确认共同控制。

## 5. 非功能需求

### 5.1 安全性

密码不得明文保存；使用 HTTPS 部署时必须保护令牌传输；后端必须进行角色、参数和业务规则校验；工具调用和关键业务操作应记录审计日志；安全知识问答只能基于审核后的资料生成。

### 5.2 可用性

页面应提供表单校验、明确错误提示、加载状态和空数据提示。预约提交后应展示预约编号和当前状态，审核驳回应展示具体原因。

### 5.3 性能

普通列表查询在模拟数据规模下平均响应时间目标不超过 2 秒；预约创建需要在事务中完成冲突检查和保存，避免并发下重复预约。

### 5.4 可维护性

业务代码按 Controller、Service、Mapper、Entity 分层；实验室业务放在若依 `ruoyi-biz` 模块；前端按页面和 API 分目录组织；状态值使用枚举或常量集中管理。

## 6. 验收标准

1. 学生、教师和管理员可以使用不同权限登录。
2. 管理员可以完成实验室和设备的增删改查及状态维护。
3. 学生可以提交预约，系统能够正确拦截时间冲突、容量超限、安全考试未通过和信用分不足。
4. 教师可以通过或驳回预约，学生可以看到审核结果和原因。
5. 预约、考试、审核和信用分数据能够在数据库中正确保存。
6. 前端页面能够通过后端接口完成上述流程。
7. 二期 Agent 只能调用授权工具，创建预约必须经过用户确认。
