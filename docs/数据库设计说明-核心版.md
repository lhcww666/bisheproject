# 数据库设计说明（核心版）

## 1. 为什么先用核心版

第一期只实现一条完整主流程：学生登录 -> 查看实验室和设备 -> 提交预约 -> 后端检查条件 -> 教师审核 -> 学生查看结果。为避免一开始表过多，核心版只保留 8 张表；耗材、签到、违规、知识库和 AI 对话表等到主流程稳定后再增加。

## 2. 命名规范

- 表名和字段名统一使用小写 `snake_case`，例如 `lab_reservation`、`start_time`。
- 主键统一命名为 `id`，类型为 `BIGINT`。
- 外键使用“实体名 + `_id`”，例如 `applicant_id`、`room_id`。
- 时间字段统一使用 `_at`，创建和修改时间为 `created_at`、`updated_at`。
- 状态使用大写英文枚举值，代码中用枚举类管理，不在业务代码中散落字符串。
- 密码字段只保存密码哈希，字段名使用 `password_hash`，禁止保存明文密码。

## 3. 核心表职责

| 表 | 作用 | 关键关联 |
| --- | --- | --- |
| `sys_user` | 学生、教师、管理员账号与信用分 | 被预约、审核、考试、信用流水引用 |
| `lab_room` | 实验室基本信息、容量和安全等级 | 一对多设备、预约 |
| `lab_device` | 设备信息和状态 | 属于一个实验室，可被预约选择 |
| `lab_reservation` | 预约申请和状态流转 | 关联申请人、实验室 |
| `reservation_device` | 预约与设备的多对多关系 | 关联预约和设备 |
| `reservation_review` | 教师审核结果和意见 | 一条预约最多一条最终审核记录 |
| `safety_exam_record` | 安全考试成绩和有效期 | 关联学生 |
| `credit_record` | 信用分变动流水 | 关联用户，当前分数在 `sys_user.credit_score` |

## 4. 预约状态流转

```text
PENDING -> APPROVED -> COMPLETED
       \-> REJECTED
PENDING/APPROVED -> CANCELED
```

后端事务必须校验：开始时间早于结束时间；人数不超过实验室容量；实验室状态为可用；同一实验室的有效预约时间不能重叠；高风险实验需要教师审核；学生安全考试在有效期内；信用分达到预约阈值。

## 5. 与若依框架的关系

如果复用若依，优先使用若依现有的用户、角色、菜单和权限表。本核心脚本中的 `sys_user` 只用于独立开发或原型验证；正式合并若依时不要保留两套用户体系。`lab_reservation.applicant_id`、`reservation_review.reviewer_id` 和 `safety_exam_record.student_id` 应改为引用若依用户表的主键。

## 6. 后续扩展表

主流程稳定后再增加：`lab_material`（耗材）、`material_apply`（领用）、`experiment_checkin`（签到）、`violation_record`（违规）、`knowledge_document`/`knowledge_chunk`（RAG 知识库）、`chat_session`/`chat_message`/`tool_call_log`（Agent 对话和审计）。这些表不应阻塞第一期开发。
