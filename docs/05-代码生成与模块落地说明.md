# 代码生成与业务模块落地说明

本文记录“从数据库表到可运行前后端页面”的完整落地过程，包含脚本执行顺序、生成器配置口径、
过程中修复的框架问题与页面验证结论，便于复现与写进论文的“实现”章节。

## 1. 落地范围

第一期把核心库的 7 张业务表全部生成前后端 CRUD 模块并跑通：

| 表 | 后端包 | 前端页面 | 菜单权限前缀 |
| --- | --- | --- | --- |
| `room` | `com.ruoyi.module.room` | `ui/src/views/module/room` | `module:room:*` |
| `device` | `com.ruoyi.module.device` | `ui/src/views/module/device` | `module:device:*` |
| `reservation` | `com.ruoyi.module.reservation` | `ui/src/views/module/reservation` | `module:reservation:*` |
| `reservation_device` | `com.ruoyi.module.reservation` | `ui/src/views/module/reservationDevice` | `module:reservationDevice:*` |
| `reservation_review` | `com.ruoyi.module.review` | `ui/src/views/module/reservationReview` | `module:reservationReview:*` |
| `safety_exam_record` | `com.ruoyi.module.safety` | `ui/src/views/module/safetyExamRecord` | `module:safetyExamRecord:*` |
| `credit_record` | `com.ruoyi.module.credit` | `ui/src/views/module/creditRecord` | `module:creditRecord:*` |

每个模块包含：`domain` / `mapper` + `Mapper.xml` / `service` / `serviceImpl` / `controller`，
以及前端 `api/module/xxx.js` 与 `views/module/xxx/index.vue`。

## 2. 数据库与生成器脚本执行顺序

```text
1. sql/ruoyi 基础脚本（若依框架表，已执行）
2. sql/module_core.sql                     业务表建表 + 实验室种子数据
3. 代码生成 -> 导入表                       把 7 张表导入 gen_table
4. sql/module/02-gen-table-config.sql      模块名/包路径/业务名/类名/字段类型口径
5. sql/module/01-module-dict.sql           枚举字段字典 + 字段字典绑定
6. 代码生成 -> 生成代码（批量）             产出 Java / Mapper / Vue / 菜单 SQL
7. sql/module/*Menu.sql                    各模块菜单与按钮权限
8. sql/module/00-module-menu-directory.sql 统一挂到“实验室业务”一级目录
```

注意：`02` 必须在“导入表”之后执行；`01` 必须在生成代码之前执行，否则枚举字段拿不到字典，
生成出的表单会缺少对应表单项。

## 3. 生成口径（与《命名规范-最终版》一致）

```text
模块名：module
包路径：com.ruoyi.module.<业务模块>
业务名：小驼峰，如 reservationDevice
类名：大驼峰，如 ReservationDevice
模板类型：element-plus（对应 ui 工程的 Vue3 + Element Plus 写法）
作者：itjialu
```

## 4. 本次修复的框架问题

生成的代码并非开箱即用，落地过程中修复了 4 处问题，均改在“源头”而不是改生成结果：

| 问题 | 现象 | 处理 |
| --- | --- | --- |
| 模板硬编码第三方作者 | 每个生成文件都带框架厂商署名与站点 | 6 个 Java 模板改用 `${author}`，由生成器配置决定 |
| 服务实现假定有 `user_id`/`dept_id` | 业务表没有这两列，编译报 `setUserId`/`setDeptId` 找不到 | 模板改为按列存在与否决定是否回填，不影响原有若依表 |
| 非字符串必填字段用 `@NotBlank` | 保存时报 `No validator could be found for constraint NotBlank` | 模板区分类型：String 用 `@NotBlank`，其它用 `@NotNull` |
| 枚举列配了 select 却没绑字典 | 表单里该字段整项不渲染（如实验室类型缺失） | 建字典类型并在 `gen_table_column` 绑定 `dict_type` |

另外两处属于表结构本身的问题：

1. `reservation_device` 原来用 `(reservation_id, device_id)` 复合主键，生成器按单列主键取 `getId()`，
   编译不通过。改为自增代理主键 `id`，原组合键降级为唯一索引，业务约束不变。
2. `open_start_time` / `open_end_time` 是 MySQL `TIME` 类型，默认映射成 `Date`，接口传 `08:00:00`
   无法反序列化。生成器配置里把这两个字段的 Java 类型改为 `String`，前端用普通文本输入。

## 5. 页面验证结论

用无头 Edge 驱动真实前端（`http://localhost:8091/admin/`）验证，18 项断言全部通过：

- 7 个模块页面全部正常渲染，侧边栏出现“实验室业务”目录；
- 实验室信息列表显示 3 条种子数据；
- “新增”弹窗可打开，且包含实验室编号、实验室类型（下拉）、状态（单选）；
- 接口新增一条 `TEST-ROOM-001` 后回到页面能看到 4 行，删除后恢复 3 行，测试数据已清理；
- 页面无 JS 报错。

验证截图：`docs/images/代码生成-实验室列表页.png`、`docs/images/代码生成-新增弹窗.png`。

## 6. 后续建议

1. 生成器产出的只是 CRUD 骨架，预约冲突校验、审核流转、资格校验仍需手写 Service（见接口设计说明书）。
2. 菜单 SQL 由生成器产出时默认挂在“系统工具”下，本仓库用 `00-module-menu-directory.sql` 统一归位，
   重新生成后记得再执行一次该脚本。
3. 每次重新导入表后，`02` / `01` 两个脚本都要重跑，否则包路径和字典绑定会回到默认值。
