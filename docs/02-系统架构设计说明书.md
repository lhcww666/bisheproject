# 校园实验室智能预约与安全管理平台系统架构设计说明书

## 1. 文档定位

本文描述 `springai` 分支当前已经实现的系统架构。早期的 `com.ruoyi.biz.lab`、`lab_room`、`/lab/...` 设计已经废弃，实际代码与数据库以本文、[数据库设计说明书](10-数据库设计说明书.md) 和 [接口设计说明书](03-接口设计说明书.md) 为准。

## 2. 设计目标

1. 完成实验室、设备、预约、审核、安全考试、信用管理和耗材库存的业务闭环。
2. 复用若依的登录、JWT、用户、角色、菜单、日志和基础管理能力。
3. 使用 Spring AI 提供受角色、工具白名单和业务规则约束的智能助手。
4. 保证 AI 不直接访问数据库，不能绕过 Java 事务执行写操作。
5. 让每次模型工具调用和预约状态变化都可追溯。

## 3. 总体架构

```text
浏览器
  |
  | Vue 3 + Element Plus + Axios
  v
Vue 前端（菜单驱动路由）
  |
  | REST API + JWT
  v
Spring Boot 3 / RuoYi
  |- ruoyi-admin       启动、配置与系统入口
  |- ruoyi-framework   安全、JWT、异常、拦截器
  |- ruoyi-system      用户、角色、菜单、部门
  |- ruoyi-common      通用基类与工具
  |- ruoyi-biz         全部实验室业务与 Agent
  |
  +--> MySQL 8：权限、业务、知识库、会话与评测
  +--> Redis：登录状态和验证码
  `--> DeepSeek：Chat 模型
```

系统采用前后端分离的单体应用。业务功能集中在 `ruoyi-biz`，不拆微服务，便于本科毕业设计部署、测试和答辩。

## 5. 前端架构

```text
ui/src
├── api/module            业务与 Agent 接口
├── views/module          业务页面
├── views/module/agent    智能助手与知识库
├── views/module/dashboard
├── router
├── store/modules
└── utils
```

- 路由由后端菜单动态生成。
- 页面按钮通过 `v-hasPermi` 和后端 `@PreAuthorize` 双重控制。
- 列表页、详情页、新增页和编辑页按单据职责拆分。
- Agent 页面拆分为会话栏、消息区和知识库弹窗组件。

## 6. 核心业务闭环

```text
安全检查与准入
  -> 学生提交预约
  -> 后端事务校验
  -> 教师审核
  -> 学生签到
  -> 学生结束实验
  -> 信用与违规处理

预约
  -> 学生申请耗材
  -> 管理员审核并扣库存
  -> 预约取消时关闭申请或归还库存
```

### 6.1 预约事务

预约创建在同一事务内完成：

1. 从 JWT 获取当前用户。
2. 校验开始时间、结束时间和参与人数。
3. 校验实验室状态、开放时间、容量、预约模式和准入范围。
4. 校验同一实验室有效预约的时间重叠。
5. 校验设备归属、状态和使用数量。
6. 校验安全考试有效期和信用分门槛。
7. 根据预约模式决定待审核或自动通过。
8. 保存主表、设备明细、审核记录和状态日志。

### 6.2 预约状态机

| 状态码 | 状态 | 主要流转 |
| --- | --- | --- |
| `0` | 待审核 | 审核通过、驳回、取消 |
| `1` | 已通过 | 签到、取消、弃审退回待审核 |
| `2` | 已驳回 | 终态 |
| `3` | 已取消 | 终态 |
| `4` | 已完成 | 终态 |
| `5` | 已签到 | 结束实验 |
| `6` | 已爽约 | 终态，可触发信用违规 |

状态机代码位于 `ReservationStateMachine`，所有动作都会写入 `reservation_status_log`。

## 7. Agent 架构

```text
用户消息
  -> AgentController
  -> AgentRoleService（从 JWT 识别角色）
  -> AgentChatClientRouter
  -> 对应角色的 ChatClient
  -> 系统提示词 + 白名单工具
  -> 业务 Service / RAG 搜索
  -> 工具审计
  -> SSE 流式回复
```

### 7.1 角色隔离

| 登录角色 | ChatClient | 主要能力 |
| --- | --- | --- |
| 学生 | 学生预约助手 | 本人资格、预约、考试、信用、可约资源和预约草稿 |
| 教师 | 教师审核助手 | 负责班级待审核预约、学生资质和班级统计 |
| 管理员 | 平台管理助手 | 全校审核概况、学生资质、规则和系统诊断 |

角色从当前登录用户解析。用户在聊天文本中冒充其他角色不会改变工具权限。

### 7.2 工具调用

- 工具通过 Spring AI `@Tool` 注册。
- 每套 ChatClient 只绑定允许的工具。
- 用户身份从后端登录上下文获取，工具不接受模型指定用户。
- 工具返回真实业务数据，模型不得自行编造。
- `tool_call_log` 保存工具名、参数、返回、状态、耗时和关联消息。

### 7.3 写操作边界

- 学生助手只能创建待确认预约草稿。
- 草稿确认由前端调用 `ReservationDraftController`，后端重新执行业务校验。
- 教师助手不提供审核写工具，最终通过/驳回/弃审在审核页面完成。
- 管理员助手不提供直接审批、修改信用或调整库存的工具。

### 7.4 RAG

- 知识文档分为安全知识和平台帮助。
- 文档可设置全部、学生、教师或管理员可见。
- 检索使用中文关键词、TF-IDF、结构匹配和本地特征哈希向量。
- 检索前按启停状态和角色范围过滤。
- 管理员可在 Agent 知识库页面维护文档和片段。

## 8. 数据与缓存

- MySQL 保存若依权限数据、业务数据、知识库、会话、草稿、审计和评测结果。
- Redis 保存登录态、验证码、限流等缓存数据。
- 完整数据库通过 [一键初始化 SQL](../sql/release/01-bishe_schema_full.sql) 建立。
- 增量结构由 `sql/module/` 中的可重复脚本维护。

## 9. 安全设计

1. 密码、JWT、菜单权限和接口权限复用若依安全体系。
2. 学生、教师、管理员按角色和数据范围访问业务数据。
3. 预约、考试、信用和库存规则在事务中检查。
4. Agent 工具使用白名单和真实登录身份。
5. AI 写操作交由页面确认，避免模型越权。
6. 工具调用和预约状态均写审计日志。
7. 真实 DeepSeek Key 只放在被 Git 忽略的本地配置或环境变量中。

## 10. 部署结构

开发环境：

- 后端：`http://localhost:8087`
- 前端：`http://127.0.0.1:8090/admin/`
- MySQL：`bishe_schema`
- Redis：`127.0.0.1:6379`

生产部署可以采用 Nginx 托管前端静态资源并反向代理后端 API。当前项目定位于单机毕业设计系统，不包含微服务、容器编排和高并发集群配置。

## 11. 当前边界

- 外部 Embedding 服务和向量数据库未接入，当前使用 MySQL 与本地特征哈希向量。
- LangChain4j 对比实现在独立分支，不属于 `springai` 主系统。
- 真实模型对话需要有效 DeepSeek Key 和网络。
- 预约成功以事务校验和最终状态为准，助手查询结果不能替代提交校验。
